# 建站元技能 2.0 — 三层架构

**设计时间**：2026-09-30  
**输入**：阶段 0 的三份调研报告（19 个可复用模式）  
**目标**：设计「诊断 → 路由 → 执行」三层架构

---

## 1. 架构概览

```
用户输入（模糊 idea / 明确需求 / 任务描述）
  ↓
┌─────────────────────────────────────────────┐
│ Layer 1: 诊断层（Diagnosis Layer）          │
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━│
│ 任务：判断用户要什么、为什么要、材料够不够   │
│ 输出：任务卡（类型 + 材料完整度 + 阻塞性缺口）│
└─────────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────────┐
│ Layer 2: 路由层（Routing Layer）            │
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━│
│ 任务：根据任务卡选择执行路径并编排 skill 链 │
│ 输出：执行计划（skill 序列 + 传参 + 汇报点） │
└─────────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────────┐
│ Layer 3: 执行层（Execution Layer）          │
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━│
│ 任务：调用现有 skill 完成具体工作           │
│ 输出：最终交付物（spec 文档 / skill / PRD） │
└─────────────────────────────────────────────┘
  ↓
交付物 + 汇报
```

## 2. Layer 1：诊断层

### 2.1 核心职责

**回答三个问题**：
1. **用户要什么？**（任务类型判断）
2. **为什么要这个？**（真实意图识别）
3. **材料够不够？**（阻塞性缺口识别）

### 2.2 输入 → 输出

**输入**：
- 用户的原始输入（可能是几个词、一段话、附件）
- 当前对话历史
- 当前工作目录状态（是否有 iterations/ 等）

**输出**：
- 任务卡（Task Card）

```markdown
## 任务卡

**任务类型**：新项目 / 迭代 / skill 化 / 重构 / 只是想法
**用户意图**：{一句话任务陈述，JTBD 格式}
**材料完整度**：丰富 / 中等 / 稀疏
**阻塞性缺口**：
  - {缺口 1}：会改变 {交付物 / 路径 / 验收}
  - {缺口 2}：...
**推荐模式**：交互 / Batch
**信心水平**：高 / 中 / 低
```

### 2.3 判断逻辑

#### 2.3.1 任务类型判断（5 种）

| 任务类型 | 识别特征 | 典型输入 |
|---------|---------|---------|
| **新项目（0→1）** | 用户说"做个 XXX"、"想做"、"帮我搭" + 无 iterations/ | "做个人作品集"<br>"我想做个产品官网" |
| **迭代（1→N）** | 用户说"加功能"、"改 XXX" + 有 iterations/ | "加个博客功能"<br>"重新设计首页" |
| **skill 化** | 用户说"反复遇到"、"沉淀成 skill"、"自动化" | "每次都要写相似的配置，能不能做成 skill" |
| **重构** | 用户说"优化"、"重构"、"改架构" + 有代码 | "把 Redux 改成 Zustand" |
| **只是想法** | 用户说"想法"、"不确定"、"有个点子" | "有个想法，不知道怎么开始" |

#### 2.3.2 材料完整度评估

**评估维度**（从 dbs-goal 的 5 条特征简化）：
- **可指物性**：能否指出最终产出什么（文件、网站、skill）
- **情境清晰**：能否知道使用场景、目标受众
- **完成边界**：能否判断什么时候算完成

**评分规则**：
- **丰富**：3 个维度都清楚 → 可以 Batch 模式或直接执行
- **中等**：2 个维度清楚 → 问 1-2 个阻塞性问题
- **稀疏**：0-1 个维度清楚 → 需要先用 dbs-jtbd 澄清任务

#### 2.3.3 阻塞性缺口识别（提问前四重判断）

**每个候选问题必须通过**：
1. 答案是否已存在于上下文？ → 是 → 直接提取
2. 能否从规格安全推出？ → 是 → 给候选判断
3. 不同答案是否会改变（交付物 / 路径 / 验收）？ → 否 → 取消提问
4. 此刻提问能否带来新决策信息？ → 否 → 取消提问

**只有通过全部判断的缺口才进入任务卡**。

### 2.4 实现方式

**方式 1：规则引擎 + LLM 判断**
- 规则引擎：检测关键词（"做个""加功能""反复"）+ 目录状态（iterations/）
- LLM 判断：当规则不确定时，让 LLM 根据上下文做最终判断

**方式 2：纯 LLM + 结构化输出**
- 给 LLM 任务类型定义 + 判断标准
- 要求输出 JSON 格式的任务卡
- 用 schema 验证输出

**推荐**：方式 2（更灵活，适合处理模糊输入）

## 3. Layer 2：路由层

### 3.1 核心职责

**根据任务卡选择执行路径并编排 skill 链**。

### 3.2 输入 → 输出

**输入**：
- Layer 1 的任务卡

**输出**：
- 执行计划（Execution Plan）

```markdown
## 执行计划

**执行路径**：路径 A / B / C / D / E
**skill 序列**：
  1. {skill-name}（{作用}）
  2. {skill-name}（{作用}）
  3. ...
**传参方式**：文件路径 / 对话上下文 / JSON
**汇报点**：每个 skill 完成后 / 整个链完成后
**预计耗时**：{估算}
**风险提示**：{如有}
```

### 3.3 路由决策树

```
任务卡
  ↓
【节点 1】材料完整度评估
  ├─ 丰富 → 【节点 2】
  ├─ 中等 → 补齐阻塞性缺口（1-2 个问题）→ 【节点 2】
  └─ 稀疏 → 路径 E（先澄清任务）
  
【节点 2】任务类型判断
  ├─ 新项目（0→1）→ 【节点 3-A】
  ├─ 迭代（1→N）→ 【节点 3-B】
  ├─ skill 化 → 【节点 3-C】
  ├─ 重构 → 【节点 3-D】
  └─ 只是想法 → 路径 E

【节点 3-A】新项目模式选择
  ├─ 材料丰富 + 用户明说 batch → 路径 A-Batch
  └─ 其他 → 路径 A-Interactive

【节点 3-B】迭代情境检查
  ├─ 有 iterations/ 且 BRIEF 存在 → 路径 B
  └─ 无 iterations/ → 提示用户（可能判断错了）→ 路径 A

【节点 3-C】skill 化问题清晰度
  ├─ 问题清楚（有反复案例）→ 路径 C-Direct
  └─ 问题模糊 → 路径 C-Clarify

【节点 3-D】重构范围
  ├─ 局部重构 → 路径 D-Local
  └─ 全局重构 → 路径 D-Global
```

### 3.4 五条执行路径

#### 路径 A：新项目（0→1）

**A-Interactive（交互模式）**：
```
skill 序列：
  1. first-flight-grill（问题定义）
  2. first-flight-brief（长期纲领）
  3. first-flight-prd（首版 PRD）
  4. first-flight-design（视觉风格）
  5. first-flight-architecture（技术选型）
  6. first-flight-content（内容填充）
  7. first-flight-agents（AI 入口）
  8. first-flight-phases（分阶段实施）

传参方式：
  - 每个 skill 读前一个 skill 生成的文件
  - 对话历史作为辅助

汇报点：
  - 每个 skill 完成后问"继续吗"
```

**A-Batch（批量模式）**：
```
skill 序列：
  1. first-flight（直接调用父 skill，batch 模式）

传参方式：
  - 传入用户描述
  - 生成 6 份骨架 + TODO 标注

汇报点：
  - 骨架生成后一次性汇报
```

#### 路径 B：迭代（1→N）

```
skill 序列：
  1. first-flight-prd（迭代模式，读 BRIEF + 上一版 PRD）
  2. first-flight-phases（实施本次迭代）

传参方式：
  - 读 BRIEF.md、上一版 PRD.md
  - 写入 iterations/v{N}-{slug}/PRD.md

汇报点：
  - PRD 完成后问"继续吗"
  - phases 完成后汇报
```

#### 路径 C：skill 化

**C-Clarify（先澄清问题）**：
```
skill 序列：
  1. dbs-goal（澄清目标）
  2. dbs-skill-maker（制作 skill）

传参方式：
  - dbs-goal 输出目标卡
  - 目标卡作为 dbs-skill-maker 的输入

汇报点：
  - 目标卡完成后展示
  - skill 完成后汇报验证等级
```

**C-Direct（问题清楚，直接制作）**：
```
skill 序列：
  1. dbs-skill-maker

传参方式：
  - 直接传入问题描述 + 反复案例

汇报点：
  - skill 完成后汇报验证等级
```

#### 路径 D：重构

```
skill 序列：
  1. wayfinder（大型重构）或 codebase-design（局部重构）

传参方式：
  - 传入重构目标 + 当前代码位置

汇报点：
  - 计划完成后展示
  - 执行完成后汇报
```

#### 路径 E：只是想法（先澄清任务）

```
skill 序列：
  1. dbs-jtbd（任务澄清）
  2. 重新诊断 → 再次进入 Layer 1

传参方式：
  - dbs-jtbd 输出任务陈述
  - 任务陈述作为新的用户输入重新诊断

汇报点：
  - 任务陈述完成后展示
  - 询问"现在明确了，要继续吗"
```

### 3.5 条件分支处理

**场景 1：材料补齐后路径变化**
```
初始诊断：材料稀疏 → 路径 E（dbs-jtbd）
  ↓
dbs-jtbd 完成后 → 重新诊断
  ↓
新诊断：任务类型 = 新项目 + 材料丰富 → 路径 A-Batch
```

**场景 2：中途发现任务类型判断错误**
```
执行路径 A（新项目）
  ↓
first-flight 检测到 iterations/ 存在 → 提示用户
  ↓
用户确认是迭代 → 切换到路径 B
```

### 3.6 实现方式

**方式：决策树 + 条件表达式**

```javascript
function selectExecutionPath(taskCard) {
  // 节点 1：材料完整度
  if (taskCard.材料完整度 === '稀疏') {
    return PATH_E; // 先澄清任务
  }
  
  if (taskCard.材料完整度 === '中等' && taskCard.阻塞性缺口.length > 0) {
    // 先问缺口，再继续
    return { action: 'ASK_GAPS', gaps: taskCard.阻塞性缺口, then: '重新诊断' };
  }
  
  // 节点 2：任务类型
  switch (taskCard.任务类型) {
    case '新项目':
      // 节点 3-A：模式选择
      if (taskCard.推荐模式 === 'Batch') {
        return PATH_A_BATCH;
      } else {
        return PATH_A_INTERACTIVE;
      }
    
    case '迭代':
      // 节点 3-B：检查 iterations/
      if (detectIterationsDir()) {
        return PATH_B;
      } else {
        return { action: 'WARN', message: '未检测到 iterations/，可能判断错误', then: PATH_A };
      }
    
    case 'skill 化':
      // 节点 3-C：问题清晰度
      if (taskCard.信心水平 === '高') {
        return PATH_C_DIRECT;
      } else {
        return PATH_C_CLARIFY;
      }
    
    case '重构':
      // 节点 3-D：范围判断
      return PATH_D;
    
    case '只是想法':
      return PATH_E;
  }
}
```

## 4. Layer 3：执行层

### 4.1 核心职责

**调用现有 skill 完成具体工作**。

### 4.2 可用 skill 清单

**First Flight 系列**（8 个）：
- `first-flight`（父 skill，入口）
- `first-flight-grill`（问题定义）
- `first-flight-brief`（长期纲领）
- `first-flight-prd`（PRD）
- `first-flight-design`（设计）
- `first-flight-architecture`（架构）
- `first-flight-content`（内容）
- `first-flight-agents`（AI 入口）
- `first-flight-phases`（分阶段实施）

**dbs 系列**（3 个）：
- `dbs-goal`（目标清晰化）
- `dbs-jtbd`（任务澄清）
- `dbs-skill-maker`（skill 制作）

**Matt Pocock 系列**（若干）：
- `wayfinder`（大型项目规划）
- `codebase-design`（代码库设计）
- ...

### 4.3 Skill 调用方式

**方式 1：直接切换（First Flight 模式）**
```
当前 skill 完成 → 告知用户"下一步：{skill-name}" → 调用下一个 skill
```

**方式 2：管道串联（AI 内参模式）**
```
Skill A 输出 → Skill B 输入 → Skill C 输入
无需用户确认（自动执行到底）
```

**建站元技能 2.0 的选择**：
- **默认：方式 1**（每步可停，尊重用户节奏）
- **可选：方式 2**（用户明确说"一次性做完"或 Batch 模式时）

### 4.4 上下文传递

**传递方式**（从 First Flight 和 AI 内参学习）：
1. **文件路径**：前一个 skill 写文件，后一个 skill 读文件
2. **对话上下文**：对话历史作为辅助（不依赖）
3. **结构化数据**：JSON 格式的中间结果

**优先级**：文件 > JSON > 对话上下文

### 4.5 错误处理

**错误类型**：
1. **Skill 不存在**：提示用户该 skill 未安装，给出安装命令
2. **Skill 执行失败**：展示错误信息，询问用户是否重试 / 跳过 / 终止
3. **中间结果不符合预期**：给用户审查机会，询问是否继续

**恢复策略**：
- **幂等设计**：支持从中断点继续（读已生成的文件）
- **检查点**：每个 skill 完成后记录状态

## 6. 三层架构的优势

### 6.1 职责分离

| 层次 | 职责 | 不做什么 |
|------|------|---------|
| **Layer 1** | 诊断判断 | 不执行具体 skill |
| **Layer 2** | 路由编排 | 不做诊断、不执行 |
| **Layer 3** | 具体执行 | 不做诊断、不做路由 |

**好处**：
- 每层职责单一，易测试
- 修改一层不影响其他层
- 可以独立优化（如换更好的诊断模型）

### 6.2 灵活性

**场景 1：新增任务类型**
- 只需修改 Layer 1 的判断逻辑
- Layer 2 添加新路径
- Layer 3 复用现有 skill

**场景 2：新增执行路径**
- Layer 1 不变
- Layer 2 添加新分支
- Layer 3 可能需要新 skill

**场景 3：优化诊断准确率**
- 只修改 Layer 1
- Layer 2 和 3 不变

### 6.3 可测试性

**Layer 1 测试**：
- 输入：用户输入 + 上下文
- 输出：任务卡
- 验证：任务类型判断准确率、缺口识别准确率

**Layer 2 测试**：
- 输入：任务卡
- 输出：执行计划
- 验证：路径选择正确性、skill 序列合理性

**Layer 3 测试**：
- 输入：执行计划
- 输出：最终交付物
- 验证：文件生成正确性、skill 调用成功率

## 7. 与现有 skill 的对比

| 维度 | First Flight | AI 内参 | 建站元技能 2.0 |
|------|-------------|---------|---------------|
| **诊断能力** | 无（假设用户要做网站）| 无（假设用户已知要什么）| 有（Layer 1）|
| **路由能力** | 有（父 skill 调度子 skill）| 有（路由表驱动）| 有（Layer 2）|
| **执行能力** | 有（8 个子 skill）| 有（多个 skill 链）| 复用现有 |
| **条件分支** | 有限（首次 vs 迭代）| 有（checkbox 触发）| 有（Layer 2）|
| **任务类型** | 1 种（做网站）| 多种（但固定）| 5 种（可扩展）|

**建站元技能 2.0 的创新**：
1. **有诊断层**：不假设用户要什么
2. **有路由层**：根据诊断结果动态选路径
3. **任务类型可扩展**：不限于"做网站"

## 8. 实现要点

### 8.1 主入口 SKILL.md 结构

```markdown
---
name: meta-builder
description: 接收模糊 idea，自主判断产出类型，链式调用 skill，从想法到交付物的元 skill
---

# meta-builder：建站元技能 2.0

## 核心能力

当用户说：
- "做个 XXX"
- "我有个想法"
- "能不能..."

我会：
1. 诊断你要什么（Layer 1）
2. 选择执行路径（Layer 2）
3. 调用对应 skill 完成（Layer 3）

## 工作流程

### Step 1：读取输入

从以下来源提取信息：
- 用户当前消息
- 对话历史
- 当前工作目录状态

### Step 2：诊断判断（Layer 1）

调用 references/diagnosis.md 中的诊断逻辑。

输出：任务卡

### Step 3：路由编排（Layer 2）

调用 references/routing.md 中的路由逻辑。

输出：执行计划

### Step 4：执行交付（Layer 3）
```

### 8.3 关键技术选择

**诊断层实现**：
- LLM + 结构化输出（JSON schema）

**路由层实现**：
- 决策树（if-else + switch）
- 条件表达式（支持重新诊断）

**执行层实现**：
- Skill 调用（直接切换，非子进程）
- 文件作为主要数据传递方式
