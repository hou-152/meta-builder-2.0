# 建站元技能 2.0 — 问题契约与行为契约

**设计时间**：2026-09-30  
**输入**：三层架构设计 + dbs 系列核心机制  
**目标**：定义元 skill 的问题契约与行为契约

---

## 1. 契约设计理念（来自 dbs-skill-maker）

### 1.1 两份契约的作用

```
问题契约（Problem Contract）
  ↓ 定义「解决什么问题」
行为契约（Behavior Contract）
  ↓ 定义「怎么解决」
SKILL.md
  ↓ 执行
验证
```

**问题契约**：
- 目标：让 AI 和人都能判断「这个问题该不该交给这个 skill」
- 内容：问题描述、适用场景、不适用场景、边界条件

**行为契约**：
- 目标：让 AI 知道「拿到问题后该做什么、怎么做、做到什么程度」
- 内容：输入输出、执行步骤、决策规则、停止条件、汇报格式

---

## 2. 问题契约

### 2.1 核心问题陈述

**建站元技能 2.0 解决的核心问题**：

> 当用户有一个模糊的 idea、任务描述或需求时，  
> 需要一个能自动判断产出类型、选择执行路径、链式调用 skill 的元 skill，  
> 以便用户不需要自己判断「该用哪个 skill」「该按什么顺序执行」。

### 2.2 适用场景

**✅ 适用（应该用 meta-builder）**：

| 场景 | 用户输入示例 | 为什么适用 |
|------|-------------|-----------|
| **模糊想法** | "我想做个作品集" | 不知道从哪开始 |
| **首次建站** | "帮我搭个产品官网" | 没用过 First Flight |
| **反复任务** | "每次写 API 文档都很麻烦，能自动化吗" | 适合 skill 化 |
| **现有项目迭代** | "给我的网站加个博客功能" | 需要判断是迭代 |
| **重构** | "把这个项目从 Redux 改成 Zustand" | 需要规划路径 |
| **不知道怎么分类** | "有个想法但不确定是做网站还是做工具" | 需要诊断 |

**❌ 不适用（不该用 meta-builder）**：

| 场景 | 用户输入示例 | 为什么不适用 | 应该用什么 |
|------|-------------|-------------|-----------|
| **明确知道要用哪个 skill** | "运行 first-flight-prd" | 用户已经知道路径 | 直接调用那个 skill |
| **只是查询信息** | "First Flight 有哪些子 skill？" | 不是执行任务 | 直接回答 |
| **纯代码实现** | "帮我写一个排序函数" | 不涉及 skill 调度 | 直接写代码 |
| **调试现有代码** | "这段代码为什么报错？" | 不是新建或迭代 | 直接调试 |
| **已经在某个 skill 中** | （用户在 first-flight-prd 过程中）"继续" | 已在执行链中 | 继续当前 skill |

### 2.3 边界条件

**边界 1：材料极度稀疏**
```
用户输入："做点东西"

判断：材料完整度 = 稀疏
行为：进入路径 E（dbs-jtbd 澄清任务），澄清后重新诊断
不应该：直接拒绝或猜测用户意图
```

**边界 2：任务超出 skill 覆盖范围**
```
用户输入："帮我写一篇文章"

判断：任务类型 = 内容创作（不在 5 种类型内）
行为：告知不适用，建议直接用对话完成
不应该：强行归类到某个类型
```

**边界 3：已有明确 skill 指令**
```
用户输入："/first-flight"

判断：用户明确指定 skill
行为：直接调用，不经过 meta-builder
不应该：拦截并重新诊断
```

**边界 4：中途发现判断错误**
```
初始诊断：新项目（0→1）
执行中发现：iterations/ 目录存在

行为：提示用户"检测到 iterations/，这可能是迭代任务，要切换到迭代模式吗？"
不应该：静默切换或继续执行错误路径
```

### 2.4 与相关 skill 的边界

| Skill | 职责边界 | meta-builder 何时调用它 |
|-------|---------|----------------------|
| **first-flight** | 建站全流程（假设用户要做网站）| 诊断确认是「新项目」且材料足够 |
| **dbs-goal** | 目标澄清（假设用户有目标但不清晰）| 诊断确认是「skill 化」但问题不清楚 |
| **dbs-jtbd** | 任务澄清（假设用户有任务但边界模糊）| 诊断确认材料稀疏（只是想法） |
| **dbs-skill-maker** | 制作 skill（假设问题已清楚）| 诊断确认是「skill 化」且问题清楚 |
| **wayfinder** | 大型项目规划（假设是代码重构）| 诊断确认是「重构」且范围大 |

**meta-builder 的独特价值**：
- 不假设用户要什么
- 自动判断该调用哪个 skill
- 支持 skill 链串联

## 3. 行为契约

### 3.1 输入输出规格

**输入**：
```markdown
## 输入类型

1. **用户消息**（必需）
   - 文本描述（几个词 → 几段话）
   - 附件（可选，如草图、参考网站、现有代码）

2. **对话历史**（可选）
   - 前几轮对话内容
   - 用于理解上下文

3. **工作目录状态**（自动检测）
   - 是否有 iterations/ 目录
   - 是否有 BRIEF.md / PRD.md
   - 是否有代码文件

## 输入约束

- 用户消息长度：无限制（但极短如"做"视为材料稀疏）
- 附件格式：Markdown、图片、代码文件
- 工作目录：必须有写权限
```

**输出**：
```markdown
## 输出类型

1. **任务卡**（诊断阶段）
   - JSON 格式
   - 给用户展示（可选，取决于信心水平）

2. **执行计划**（路由阶段）
   - Markdown 格式
   - 展示 skill 序列、预计耗时

3. **中间汇报**（执行阶段）
   - 每个 skill 完成后汇报
   - 包含生成的文件、关键内容、下一步

4. **最终交付**（完成阶段）
   - 文件清单
   - 验证结果
   - 使用建议

## 输出约束

- 任务卡必须包含全部字段（不能有 null）
- 执行计划必须有至少 1 个 skill
- 汇报必须包含文件路径（可点击）
```

### 3.2 执行步骤规格

```markdown
## Step 1：读取输入（必需）

**动作**：
- 读取用户当前消息
- 读取对话历史（最近 3 轮）
- 检测工作目录状态（ls、检查特定文件）

**输出**：
- 原始输入对象（JSON）

**停止条件**：
- 无，总是执行

---

## Step 2：诊断判断（必需）

**动作**：
- 调用 references/diagnosis.md 逻辑
- 生成任务卡

**输出**：
- 任务卡（JSON）

**决策点**：
- 信心水平 = 低 → 展示任务卡，询问用户确认
- 信心水平 = 中/高 → 直接进入 Step 3

**停止条件**：
- 任务超出覆盖范围 → 告知不适用，停止

---

## Step 3：路由编排（必需）

**动作**：
- 调用 references/routing.md 逻辑
- 生成执行计划

**输出**：
- 执行计划（JSON）

**决策点**：
- 材料完整度 = 中等 + 有阻塞性缺口 → 先提问，等用户回答，重新诊断
- 材料完整度 = 稀疏 → 进入路径 E（dbs-jtbd）
- 其他 → 选择对应路径

**停止条件**：
- 无可用 skill → 提示缺少依赖，停止

---

## Step 4：展示执行计划（可选）

**动作**：
- 将执行计划展示给用户
- 询问"要继续吗？"

**触发条件**：
- 推荐模式 = 交互（Interactive）
- 或信心水平 = 低

**跳过条件**：
- 推荐模式 = Batch
- 且信心水平 = 高

**停止条件**：
- 用户回答"不"→ 停止

---

## Step 5：执行 Skill 链（必需）

**动作**：
- 按执行计划中的 skill 序列逐个调用
- 每个 skill 完成后汇报

**汇报格式**：
```markdown
✅ 已完成：{skill-name}

**生成文件**：{文件路径}（可点击）

**关键内容**：
- {要点 1}
- {要点 2}

**下一步**：{下一个 skill-name}（{作用}）

要继续吗？
```

**决策点**：
- 推荐模式 = 交互 → 每个 skill 后等用户确认
- 推荐模式 = Batch → 自动继续

**错误处理**：
- Skill 不存在 → 提示安装命令，停止
- Skill 执行失败 → 展示错误，询问"重试/跳过/停止"
- 用户说"停止" → 立即停止

**停止条件**：
- skill 序列全部完成 → 进入 Step 6
- 遇到无法恢复的错误 → 停止
- 用户明确说停止 → 停止

---

## Step 6：最终汇报（必需）

**动作**：
- 列出所有生成的文件
- 展示验证结果（如有）
- 给出下一步建议

**汇报格式**：
```markdown
🎉 任务完成

**生成文件**（{N} 个）：
- `{路径 1}`（{作用}）
- `{路径 2}`（{作用}）

**验证结果**：
- ✅ {检查项 1}
- ✅ {检查项 2}

**下一步建议**：
- {建议 1}
- {建议 2}

有问题随时问我 🚀
```

**停止条件**：
- 汇报完成即停止
```

### 3.3 决策规则规格

**规则 1：材料完整度判断**
```
输入：用户消息 + 上下文
输出：丰富 / 中等 / 稀疏

判断依据：
- 可指物性：能否说出具体产出？
- 情境清晰：能否知道使用场景？
- 完成边界：能否判断何时算完成？

计分：
- 3 个都清楚 → 丰富
- 2 个清楚 → 中等
- 0-1 个清楚 → 稀疏
```

**规则 2：任务类型判断**
```
输入：用户消息 + 工作目录状态
输出：新项目 / 迭代 / skill 化 / 重构 / 只是想法

判断依据：
1. 关键词匹配（"做个""加功能""反复""优化""想法"）
2. 目录状态（有无 iterations/、BRIEF.md）
3. LLM 综合判断（前两者不确定时）

优先级：
- 目录状态 > 关键词 > LLM 判断
```

**规则 3：阻塞性缺口识别**
```
输入：候选问题列表
输出：过滤后的阻塞性缺口列表

过滤规则（四重判断）：
1. 答案是否已在上下文？ → 是 → 删除
2. 能否从规格安全推出？ → 是 → 删除
3. 不同答案是否会改变（交付物 / 路径 / 验收）？ → 否 → 删除
4. 此刻提问能否带来新决策信息？ → 否 → 删除

保留：
- 通过全部 4 个判断的问题
```

**规则 4：模式选择（交互 vs Batch）**
```
输入：任务卡
输出：交互 / Batch

判断依据：
- 用户明说"一次性做完" → Batch
- 材料完整度 = 丰富 + 信心水平 = 高 → 建议 Batch，但默认交互
- 其他 → 交互
```

**规则 5：路径选择**
```
输入：任务卡
输出：路径 A / B / C / D / E

判断逻辑：见「三层架构.md」第 3.3 节决策树
```

### 3.4 停止条件规格

**主动停止（预期内）**：
1. **Skill 链执行完成** → 正常结束
2. **用户明确说停止** → 立即停止
3. **任务超出覆盖范围** → 告知后停止

**被动停止（意外）**：
1. **Skill 不存在** → 提示后停止
2. **Skill 连续失败 3 次** → 停止
3. **无法恢复的错误**（如文件系统故障）→ 停止

**中途暂停（可恢复）**：
1. **等待用户确认**（交互模式）→ 用户回复后继续
2. **提问阻塞性缺口** → 用户回答后重新诊断

### 3.5 汇报格式规格

**任务卡展示**（信心水平 = 低时）：
```markdown
## 📋 任务诊断

我理解你想做的是：**{用户意图}**

**任务类型**：{类型}  
**材料完整度**：{丰富/中等/稀疏}

{如果有阻塞性缺口}
**还需要确认**：
1. {缺口 1}（会影响 {影响}）
2. {缺口 2}（会影响 {影响}）

我的判断对吗？
```

**执行计划展示**：
```markdown
## 🗺️ 执行计划

**路径**：{路径名}

**将执行以下 skill**：
1. {skill-name}（{作用}）
2. {skill-name}（{作用}）
3. ...

**预计耗时**：{估算}

{如果有风险提示}
**⚠️ 注意**：{风险}

要开始吗？
```

**中间汇报**：见 3.2 Step 5

**最终汇报**：见 3.2 Step 6

## 4. 契约验证标准

### 4.1 问题契约验证

**验证方式**：6 个测试样本（来自阶段 3）

| 样本 | 期望行为 | 验证点 |
|------|---------|-------|
| **S1** | 判断为「新项目」 | 任务类型准确 |
| **S2** | 判断为「迭代」 | 检测到 iterations/ |
| **S3** | 判断为「skill 化」 | 识别"反复"关键词 |
| **S4** | 判断为「重构」 | 识别代码改造需求 |
| **S5** | 判断为「只是想法」→ 澄清后重新判断 | 材料稀疏处理 |
| **S6** | 告知不适用 | 超出范围拒绝 |

**通过标准**：
- S1-S5 判断正确率 100%
- S6 正确拒绝
- 无误报（不该拒绝的被拒绝）

### 4.2 行为契约验证

**验证方式**：实际执行 6 个样本

| 验证点 | 通过标准 | 测试方法 |
|-------|---------|---------|
| **输入处理** | 读取用户消息 + 检测目录状态 | 检查日志 |
| **任务卡生成** | JSON 格式正确 + 所有字段非空 | Schema 验证 |
| **路径选择** | 与期望路径一致 | 对比执行计划 |
| **Skill 调用** | 成功调用 + 生成文件 | 检查文件存在 |
| **汇报格式** | 符合规格 + 文件路径可点击 | 人工检查 |
| **停止条件** | 正常结束或正确停止 | 检查最终状态 |

**通过标准**：
- 6 个样本全部执行成功
- 无中途崩溃或无限循环
- 汇报格式符合规格

## 5. 契约演进机制

### 5.1 何时修改问题契约

**场景 1：发现新的适用场景**
```
用户反馈："我想用 meta-builder 做 XXX，但它说不适用"

处理：
1. 评估该场景是否真的适用
2. 适用 → 添加到「适用场景」表
3. 不适用 → 添加到「不适用场景」表 + 说明原因
```

**场景 2：边界模糊导致误用**
```
发现：用户在不该用的时候用了，或该用的时候没用

处理：
1. 识别模糊边界
2. 添加到「边界条件」章节
3. 更新诊断逻辑
```

### 5.2 何时修改行为契约

**场景 1：执行步骤有遗漏**
```
发现：某个步骤没考虑到某种情况

处理：
1. 添加决策点或条件分支
2. 更新「执行步骤规格」
```

**场景 2：决策规则不准确**
```
发现：任务类型判断错误率高

处理：
1. 分析错误案例
2. 调整判断依据或优先级
3. 更新「决策规则规格」
```

**场景 3：汇报格式不清晰**
```
用户反馈："不知道生成了什么文件"

处理：
1. 优化汇报格式
2. 添加更多信息（如文件作用）
```

### 5.3 版本管理

```
契约版本号：{Major}.{Minor}

Major 变更（不兼容）：
- 修改输入输出格式
- 删除某个执行步骤
- 改变核心决策规则

Minor 变更（兼容）：
- 添加新的适用场景
- 优化汇报格式
- 添加新的决策分支（不影响现有路径）
```

**当前版本**：1.0

## 6. 与 dbs 系列契约的对比

| 维度 | dbs-goal | dbs-jtbd | dbs-skill-maker | meta-builder |
|------|----------|----------|----------------|-------------|
| **问题契约焦点** | 目标不清晰 | 任务边界模糊 | 反复遇到同类问题 | 不知道用哪个 skill |
| **行为契约焦点** | 澄清目标 | 澄清任务 | 制作 skill | 判断 + 路由 + 执行 |
| **输入要求** | 有目标但不清晰 | 有任务但边界模糊 | 问题清楚 | 可以模糊 |
| **输出产物** | 目标卡 | 任务陈述 | SKILL.md | 多种（取决于路径）|
| **是否调用其他 skill** | 否 | 否 | 否 | 是（核心能力）|

**meta-builder 的特殊性**：
- 是唯一一个「调用其他 skill」的 skill
- 输入可以极度模糊（其他 skill 都有基本要求）
- 输出取决于诊断结果（不固定）
