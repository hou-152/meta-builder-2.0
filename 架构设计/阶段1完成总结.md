## 🔑 关键发现

### 1. 三层职责分离的价值

**发现**：三层架构不是为了"看起来工整"，而是为了解决真实问题。

**证据**：
- **Layer 1 独立**：诊断逻辑可以单独优化（如换更好的 LLM），不影响路由和执行
- **Layer 2 灵活**：新增任务类型只需修改路由层，不动诊断和执行
- **Layer 3 复用**：执行层直接调用现有 skill，不重复造轮子

**对比**：
- First Flight：没有独立诊断层，假设用户要做网站
- AI 内参：没有独立路由层，事件 → skill 映射固定
- 建站元技能 2.0：三层分离，可以处理「不知道要什么」的输入

### 2. 阻塞性缺口识别是关键

**发现**：不是所有问题都该问，只问「改变交付物/路径/验收」的问题。

**证据**（来自 dbs 系列的四重判断）：
1. 答案已在上下文？ → 直接提取
2. 能从规格推出？ → 给候选判断
3. 不同答案改变结果？ → 否 → 不问
4. 此刻问有新信息？ → 否 → 不问

**效果**：
- 避免「为了完整性」而过度提问
- 每个问题都必须有明确的决策价值

### 3. 路径 E（先澄清任务）是兜底能力

**发现**：路径 E 不是「失败路径」，而是「适应模糊输入」的能力。

**流程**：
```
材料稀疏 → dbs-jtbd 澄清任务 → 重新诊断 → 新路径
```

**价值**：
- 用户可以用极度模糊的输入（"有个想法"）
- 系统不会直接拒绝或猜测
- 澄清后自动选择正确路径

**对比**：
- First Flight：必须明确要做网站
- dbs-goal/jtbd：用户必须有基本目标或任务
- 建站元技能 2.0：可以从「只是想法」开始

### 4. 条件分支处理是稳健性保障

**发现**：真实场景中会有判断错误、skill 缺失、中途变化，必须有应对机制。

**三个关键分支**：
1. **补齐缺口后路径变化**：材料从「中等」变「丰富」，可以从 Interactive 切到 Batch
2. **中途发现判断错误**：诊断为「新项目」但检测到 iterations/，提示用户确认
3. **Skill 不存在降级**：dbs-skill-maker 未安装，提供「安装/手动/停止」选项

**价值**：
- 不会因为一个错误判断就崩溃
- 给用户纠正的机会
- 有降级方案

### 5. 决策树可测试性

**发现**：6 个测试样本可以覆盖所有关键路径和分支。

**样本覆盖**：
- S1：新项目（丰富材料）→ PATH_A_INTERACTIVE
- S2：迭代（有 iterations/）→ PATH_B
- S3：skill 化（问题清楚）→ PATH_C_DIRECT
- S4：重构（全局）→ PATH_D_GLOBAL
- S5：只是想法 → PATH_E → 重新路由
- S6：超出范围 → 拒绝

**验证点**：
- 任务类型判断准确率
- 路径选择正确性
- 条件分支触发正确性
- 拒绝场景正确性
