## 测试执行流程

### 推荐执行顺序

**第一批（基础路径，30-45 分钟）**：
1. S1 — 新项目 Interactive（验证标准流程）
2. S6 — 超出范围拒绝（快速验证边界）
3. S3 — skill 化 Direct（验证高信心路径）
4. S2 — 迭代 + 缺口提问（验证材料补齐）

**第二批（复杂路径，45-60 分钟）**：
5. S4 — 全局重构（验证重构范围判断）
6. S5 — 递归重诊断（验证极度模糊输入处理）
7. S10 — 冲突纠错（验证中途判断修正）

**第三批（新增路径，30-45 分钟）**：
8. S7 — Batch 模式（验证一次性生成）
9. S8 — Clarify 模式（验证两阶段 skill 化）
10. S9 — 局部重构（验证局部 vs 全局判断）

**总预计耗时**：105-150 分钟

## 单个样本测试步骤

### Step 1：环境准备

```bash
# 创建测试目录
mkdir -p /tmp/meta-builder-test/s{N}
cd /tmp/meta-builder-test/s{N}

# 按样本要求准备环境
# （见 `测试/样本集.md` 中每个样本的"环境准备"部分）
```

---

### Step 2：调用 meta-builder

```
在 AI 环境中输入：
/meta-builder
```

---

### Step 3：输入用户消息

```
粘贴样本的"用户输入"部分文本
```

示例（S1）：
```
做个人作品集网站，展示我的设计作品。目标受众是潜在雇主。包含首页、作品列表、作品详情、关于我。
```

---

### Step 4：观察 AI 输出

**关键观察点**：

1. **诊断阶段输出**：
   - 是否输出了任务卡（Task Card）？
   - 任务类型判断是否正确？
   - 材料完整度评估是否准确？
   - 阻塞性缺口识别是否合理？

2. **提问阶段（如有）**：
   - 是否提出了阻塞性问题？
   - 问题是否真的"改变结果"？
   - 是否有不必要的提问？

3. **路由阶段输出**：
   - 是否输出了执行计划（Execution Plan）？
   - 执行路径选择是否正确？
   - skill 序列是否合理？

4. **执行阶段**：
   - 是否按顺序调用了 skill？
   - 每个 skill 的输入输出是否正确？
   - 是否有错误或降级处理？

---

### Step 5：记录实际结果

在 `测试/行为测试结果.md` 中记录（见下方模板）

---

### Step 6：对比期望结果

打开 `测试/样本集.md`，找到对应样本的"期望诊断结果"和"期望路由结果"

**逐项对比**：

- 材料完整度是否一致？
- 阻塞性缺口数量和内容是否一致？
- 执行路径是否一致？
- skill 序列是否一致？

## 常见问题与处理

### 问题 1：依赖 skill 不存在

**现象**：路由选择正确，但执行时报错"skill not found"

**处理**：
1. 记录为"降级逻辑验证"
2. 检查是否触发了降级提示（应该提示安装命令）
3. 不算作 meta-builder 本身的失败

---

### 问题 2：判断与期望完全不同

**现象**：任务类型、路径选择完全错误

**处理**：
1. 标记为"失败"
2. 详细记录实际输出
3. 分析根因（关键词匹配？LLM 判断？目录状态检测？）
4. 在 `测试/失败归因与修复.md` 中记录

---

### 问题 3：部分验证点失败

**现象**：任务类型正确，但材料完整度评估不准

**处理**：
1. 标记为"部分通过"
2. 计算通过率（如 4/5 = 80%）
3. 分析具体哪个维度（可指物性？情境清晰？完成边界？）
4. 记录建议修复

---

### 问题 4：提问过多或过少

**现象**：
- 过多：材料明明够了，还在问
- 过少：材料不够，没有提问

**处理**：
1. 标记为"阻塞性缺口识别失败"
2. 检查四重判断是否被正确执行
3. 记录具体案例

---

### 问题 5：中途卡住

**现象**：诊断完成，但没有输出执行计划

**处理**：
1. 检查是否在等待用户确认
2. 检查是否触发了停止条件
3. 检查路由层是否报错

## 测试完成后

### 1. 生成测试报告

整理 `测试/行为测试结果.md`，包含：
- 每个样本的详细结果
- 验证点通过率统计
- 失败样本的根因分析
- 修复建议优先级排序

---

### 2. 修复失败样本（如有）

按优先级修复 `diagnosis.md` 或 `routing.md`：

**高优先级**（必须修复）：
- 任务类型判断完全错误
- 执行路径选择错误
- 阻塞性提问逻辑失效

**中优先级**（建议修复）：
- 材料完整度评估偏差
- 信心水平计算不准
- 提问数量不合理

**低优先级**（可接受）：
- 用户意图 JTBD 格式不完美
- 预计耗时偏差
- 汇报格式细节

---

### 3. 重新测试修复样本

只重新测试失败的样本，验证修复效果

---

### 4. 更新项目总结

在 `项目完成总结.md` 中补充：
- 阶段 3.2 完成状态
- 测试通过率
- 实际发现的问题
- 修复后的最终状态

---

## 测试成功标准

### 最低标准（可接受）

- 通过率 ≥ 70%（7/10）
- 核心路径（A-Interactive、B、E）全部通过
- 无严重逻辑错误（如超出范围却执行、新项目判断为迭代）

### 理想标准（优秀）

- 通过率 ≥ 90%（9/10）
- 所有路径至少通过 1 个样本
- 阻塞性缺口识别准确率 ≥ 80%

### 完美标准（极致）

- 通过率 = 100%（10/10）
- 所有验证点全部通过
- 无任何不必要提问
