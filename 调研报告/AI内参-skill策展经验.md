# AI 内参 Skill 策展经验

**调研时间**：2026-09-30  
**调研对象**：`~/CLAUDE.md` Agent 路由表 + 全局约束 + 通用约定  
**调研目标**：学习如何设计 skill 链式调用、条件触发、数据传递、幂等性

---

## 1. Agent 路由表设计

### 1.1 路由表结构

AI 内参使用**三列路由表**设计：

| Agent | 触发条件 | 执行链 |
|-------|---------|--------|
| 龙虾日报 | 每日凌晨 cron / 手动指令 | 龙虾日报 skill |
| 日报排版 | 日报数据库新建页面 / @mention | 日报排版 skill |
| 精选入库 | 日报「精选入库？」✅ | 文章入库 skill → 阅读提醒 skill |
| 概念提取入库 | 阅读库「概念提取+入库？」✅ | 概念提取 skill → 概念入库 skill |
| 深度处理 | 阅读库「DaCapo 标注版」更新 | 三级笔记 skill → 概念提取 skill → 概念入库 skill |
| Changelog | 手动指令 / @mention「changelog」 | changelog skill |

### 1.2 设计特点

**1. 触发条件多样化**
- **时间触发**：每日凌晨 cron（定时任务）
- **数据触发**：数据库新建页面（Notion webhook）
- **用户触发**：手动指令 / @mention（人工启动）
- **状态触发**：checkbox ✅（条件满足）
- **内容触发**：特定字段更新（如「DaCapo 标注版」字段变化）

**2. 执行链清晰**
- 单一 skill：`龙虾日报 skill`
- 链式 skill：`文章入库 skill → 阅读提醒 skill`
- 多级 skill：`三级笔记 skill → 概念提取 skill → 概念入库 skill`

**3. 设计洞察**

> Agent 路由表本质是「事件 → 处理流程」的映射表。

关键是：
- **触发条件明确**：不模糊（不是"可能""有时"）
- **执行链确定**：从左到右，无分支（分支逻辑在 skill 内部）
- **边界清晰**：每个 Agent 负责一类事件，不重叠

## 2. Skill 链式调用机制

### 2.1 单向箭头（→）的含义

```
文章入库 skill → 阅读提醒 skill
```

**语义**：
- 文章入库完成后，**自动**调用阅读提醒
- 不需要用户确认（"串联执行：Agent 链中的后续 skill 直接继续执行，无需向 Da Capo 确认"）
- 前一个 skill 的输出是后一个 skill 的输入

### 2.2 三级链式调用

```
三级笔记 skill → 概念提取 skill → 概念入库 skill
```

**执行顺序**：
1. 三级笔记 skill 处理「DaCapo 标注版」内容
2. 输出标注内容 → 传递给概念提取 skill
3. 概念提取 skill 提取概念 → 传递给概念入库 skill
4. 概念入库 skill 写入数据库

**设计洞察**：

> 链式调用的本质是「管道」（Pipeline）：每个 skill 是一个处理节点，输出成为下一个节点的输入。

### 2.3 与 First Flight 的对比

| 维度 | First Flight | AI 内参 |
|------|-------------|---------|
| **调用方式** | 子 skill 切换（父 skill 调度） | 自动串联（无父 skill） |
| **上下文传递** | 读文件 + 对话历史 | 数据库状态 + 页面链接 |
| **中断机制** | 每步问"继续吗" | 直接执行到底（幂等设计） |
| **错误处理** | 用户介入 | 失败汇报（comment @Da Capo） |

## 3. 条件触发机制

### 3.1 Notion Checkbox 触发

```
触发条件：日报「精选入库？」✅
执行链：文章入库 skill → 阅读提醒 skill
```

**工作流程**：
1. 用户在日报数据库页面勾选「精选入库？」checkbox
2. Notion webhook 通知 Agent
3. Agent 检测到 checkbox = true
4. 启动执行链

### 3.2 字段更新触发

```
触发条件：阅读库「DaCapo 标注版」更新
执行链：三级笔记 skill → 概念提取 skill → 概念入库 skill
```

**工作流程**：
1. 用户在阅读库页面编辑「DaCapo 标注版」字段
2. Notion webhook 通知 Agent
3. Agent 检测到字段内容变化
4. 启动执行链

### 3.3 设计洞察

**条件触发的本质是「状态机」**：
- 状态从 A（未勾选）→ B（已勾选）
- 状态转换触发动作
- 动作完成后不影响状态（幂等性）

**与 First Flight 的区别**：
- First Flight：用户主动说"我要做 XXX" → 启动流程
- AI 内参：用户改变数据状态 → 自动启动流程

## 4. Skill 间数据传递

### 4.1 传递方式

**方式 1：Notion 页面链接**
```
文章入库 skill 创建新页面 → 返回页面 URL → 阅读提醒 skill 使用该 URL
```

**方式 2：数据库查询**
```
概念提取 skill 写入临时结果 → 概念入库 skill 查询并读取
```

**方式 3：会话上下文**
```
三级笔记 skill 在对话中输出结果 → 下一个 skill 从对话历史读取
```

### 4.2 数据传递的设计原则

**原则 1：数据库是唯一真实来源**
- 不依赖对话历史（对话可能中断）
- 不依赖内存变量（会话重启后丢失）
- 所有中间结果写入 Notion 数据库

**原则 2：页面链接是传递凭证**
- 前一个 skill 返回页面 URL
- 后一个 skill 用 URL 读取页面内容
- URL 是不可变的（页面移动后 URL 仍有效）

**原则 3：最小化传递内容**
- 不传递全文（传 URL 让下游自己读）
- 不传递中间状态（只传最终结果）
- 不传递配置（读全局配置文件）

### 4.3 与 First Flight 的对比

| 维度 | First Flight | AI 内参 |
|------|-------------|---------|
| **数据载体** | 本地文件（.md） | Notion 数据库（页面） |
| **传递方式** | 读文件路径 | 读页面 URL |
| **持久化** | Git 版本控制 | Notion 版本历史 |
| **并发安全** | 单用户（无并发） | 多 Agent（需幂等） |

## 5. 幂等性设计

### 5.1 什么是幂等性？

**定义**：同一个操作执行多次，结果与执行一次相同。

**例子**：
- ✅ 幂等：「设置标题为 XXX」（重复执行，标题还是 XXX）
- ❌ 非幂等：「标题追加 XXX」（重复执行，标题变成 XXX XXX XXX）

### 5.2 AI 内参的幂等设计

**场景 1：重复勾选 checkbox**
- 用户不小心取消勾选 → 再次勾选
- Agent 再次触发 → 但数据库中已有该文章
- **幂等处理**：检查文章是否已存在 → 跳过重复入库

**场景 2：重复更新「DaCapo 标注版」**
- 用户多次编辑标注内容
- Agent 多次触发概念提取
- **幂等处理**：覆盖旧概念 → 保持最新版本

**场景 3：重复运行 changelog**
- 用户多次调用 changelog skill
- **幂等处理**：读取同一时间段的 Git log → 生成相同 changelog

### 5.3 幂等性的实现策略

**策略 1：检查后执行**
```
if (文章 URL 已存在于阅读库):
    跳过入库
else:
    写入阅读库
```

**策略 2：覆盖而非追加**
```
# ❌ 非幂等
概念列表.append(新概念)

# ✅ 幂等
概念列表 = 提取的所有概念（完整替换）
```

**策略 3：唯一标识符**
```
文章 ID = URL hash
if (阅读库中存在该 ID):
    更新内容
else:
    创建新页面
```

### 5.4 设计洞察

**为什么需要幂等性？**

> 因为触发条件可能重复发生（用户误操作、webhook 重发、网络重试）。

**First Flight 不需要幂等性的原因**：
- 用户主动驱动，不会无意触发两次
- 本地文件覆盖，天然幂等
- 没有外部 webhook，无重复触发风险

## 6. 进度汇报机制

### 6.1 汇报方式

**核心原则**：
> 在目标页面发一条 comment，@Da Capo。不要在每个概念/文章页面单独发消息。

**例子**：
```
在日报页面 comment：
「✅ 已入库 3 篇文章到阅读库，已发送飞书提醒。@Da Capo」
```

### 6.2 汇报时机

**成功时**：
- 整个执行链完成后汇报一次
- 不是每个 skill 完成都汇报

**失败时**：
- 立即汇报，说明失败原因
- 提供足够信息让用户判断是否重试

### 6.3 汇报内容

**必须包含**：
- ✅ 完成状态（成功/失败/部分成功）
- 📊 数量统计（处理了多少条）
- 🔗 相关链接（生成的页面 URL）
- @Da Capo（确保用户看到）

**不包含**：
- 中间过程日志（放在 Agent 内部日志）
- 敏感信息（API key、内部 ID）
- 过长的内容（用"查看详情"链接）

### 6.4 与 First Flight 的对比

| 维度 | First Flight | AI 内参 |
|------|-------------|---------|
| **汇报对象** | 用户（对话中） | 用户（Notion comment） |
| **汇报时机** | 每步完成 | 整个链完成 |
| **汇报方式** | 对话消息 | @mention |
| **确认机制** | 问"继续吗" | 不需要确认（自动执行） |

## 7. 全局约束的设计智慧

### 7.1 技术约束

**Readwise 内容获取规则**：
> 必须使用 Readwise MCP 工具通过 API 获取内容，绝对不要直接 view `readwise.io` 网页 URL（会触发 Notion 外部 URL 安全审核弹窗）。

**洞察**：
- 不是所有可行的技术路径都应该使用
- 优先选择"不会触发外部副作用"的路径
- API > 网页抓取（安全性、稳定性）

### 7.2 流程约束

**Skill 页面是唯一真实来源**：
> Agent 指令只包含触发条件、执行顺序、关键规则提醒。完整 Step 1–N 操作手册在 Notion skill 页面中。

**洞察**：
- Agent 路由表是"索引"，不是"手册"
- 细节在 skill 文档中（单一真实来源）
- 路由表保持简洁，避免信息冗余

### 7.3 决策约束

**Select 选项直接新增**：
> 新作者、新标签、新领域等直接新增，无需向 Da Capo 确认。

**洞察**：
- 不是所有决策都需要人工参与
- 低风险决策自动化（新增标签）
- 高风险决策人工介入（删除数据）

### 7.4 执行约束

**串联执行无需确认**：
> Agent 链中的后续 skill 直接继续执行，无需向 Da Capo 确认。

**洞察**：
- 链式调用的前提是"用户已授权整个链"
- 不是每步都问"继续吗"（降低打扰）
- 失败时汇报，成功时静默

## 8. 可提取的元 skill 设计模式

### 8.1 模式 1：「事件驱动」触发

```
数据状态变化（checkbox / 字段更新）→
  检测变化类型 →
  查路由表 →
  启动对应执行链
```

**可复用点**：
- 不依赖用户主动说话
- 数据库状态是触发源
- 路由表是决策依据

### 8.2 模式 2：「管道式」skill 链

```
Skill A 输出 → Skill B 输入 → Skill C 输入
```

**可复用点**：
- 每个 skill 专注一件事
- 输出标准化（URL / JSON）
- 无需父 skill 调度（自动串联）

### 8.3 模式 3：「幂等执行」保证

```
执行前检查：
  if (已存在):
    跳过 / 更新
  else:
    创建
```

**可复用点**：
- 支持重复触发（不怕误操作）
- 结果一致性（多次执行 = 一次执行）
- 降低失败成本（重试安全）

### 8.4 模式 4：「最终汇报」机制

```
执行链 A → B → C
  ↓
完成后统一汇报（而非每步汇报）
```

**可复用点**：
- 减少打扰（一次汇报 vs 三次汇报）
- 信息聚合（整体结果 vs 零散信息）
- 明确责任（谁汇报 = 谁负责整个链）

### 8.5 模式 5：「数据库作为真实来源」

```
所有中间结果 → 写入数据库
所有后续 skill → 从数据库读取
不依赖对话历史 / 内存
```

**可复用点**：
- 持久化（会话重启不丢失）
- 可追溯（数据库有版本历史）
- 并发安全（多 Agent 同时运行）

### 8.6 模式 6：「路由表驱动」架构

```
路由表 = 【触发条件 → 执行链】映射
Agent 只需：
  1. 监听事件
  2. 查路由表
  3. 执行对应链
```

**可复用点**：
- 配置与逻辑分离
- 新增 Agent 只需添加路由表行
- 修改流程不改代码（改路由表）

## 9. 关键发现总结

### 9.1 AI 内参的本质是什么？

**不是"任务执行器"，而是"事件响应系统"**。

它假设用户通过改变数据状态（勾选 checkbox、更新字段）表达意图，Agent 监听这些事件并自动执行对应流程。

### 9.2 为什么需要 skill 链而非单一 skill？

**因为"一件复杂的事"可以拆成"多个简单的事"**：
- 文章入库（写数据库）
- 阅读提醒（发通知）

拆分后：
- 每个 skill 职责单一，易测试
- 可以单独调用（如只入库，不提醒）
- 可以灵活组合（入库 → 提醒 → 统计）

### 9.3 什么是"可复用的策展经验"？

**6 个模式**：
1. 「事件驱动」触发
2. 「管道式」skill 链
3. 「幂等执行」保证
4. 「最终汇报」机制
5. 「数据库作为真实来源」
6. 「路由表驱动」架构

## 10. 对建站元技能 2.0 的启示

### 10.1 可直接复用的设计

1. **路由表**：触发条件 → 执行链的映射
2. **管道式链**：Skill A → B → C 自动串联
3. **幂等设计**：支持重复触发，结果一致
4. **最终汇报**：整个链完成后统一汇报
5. **数据作为真实来源**：不依赖对话历史

### 10.2 需要适配的地方

**AI 内参的特点**：
- 触发源是 Notion 数据库（checkbox / 字段更新）
- 数据载体是 Notion 页面（URL）
- 汇报方式是 Notion comment（@mention）

**建站元技能 2.0 的特点**：
- 触发源是用户输入（对话消息）
- 数据载体是本地文件（.md / JSON）
- 汇报方式是对话回复（markdown）

**需要调整**：
1. **触发机制**：从"数据状态变化"改为"用户意图识别"
2. **数据传递**：从"Notion URL"改为"文件路径"
3. **汇报方式**：从"comment @mention"改为"对话消息"
4. **幂等设计**：从"检查数据库"改为"检查文件存在性"

### 10.3 可创新的方向

**AI 内参没有但建站元技能 2.0 需要的**：
1. **诊断层**：判断用户要什么（AI 内参假设用户已知要什么）
2. **条件分支**：根据诊断结果选路径（AI 内参的路径是固定的）
3. **交互 vs Batch**：AI 内参没有这个概念（都是自动执行）
4. **预览机制**：AI 内参直接写数据库（建站元技能需要预览确认）
