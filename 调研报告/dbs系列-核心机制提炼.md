# dbs 系列核心机制提炼

**调研时间**：2026-09-30  
**调研对象**：`dbs-goal`、`dbs-jtbd`、`dbs-skill-maker` 三个 skill  
**调研目标**：提取「诊断 → 判断 → 执行」模式，学习阻塞性缺口识别、问题契约到行为契约的转换

---

## 1. dbs 系列的共同哲学

### 1.1 核心假设

**三个 skill 共享一个底层假设**：

> 用户说的话，往往不是最终要做的事。

- **dbs-goal**：用户说"做个人 IP"，但"个人 IP"不是可执行的目标
- **dbs-jtbd**：用户说"帮我写一篇文章"，但"文章"只是手段，真正的任务是推进某种进展
- **dbs-skill-maker**：用户说"做个 skill"，但 skill 本身不是目的，解决反复问题才是

### 1.2 工作方式

**三个 skill 都遵循同一个流程**：

```
用户输入（往往是方案语言）
  ↓
提取真实意图（任务语言 / 目标语言 / 问题语言）
  ↓
识别阻塞性缺口（只问会改变结果的问题）
  ↓
生成可执行的交付物
```

### 1.3 设计洞察

**"意义即使用"（Meaning as Use）**：

> 一个词的意义要看它在当前任务中产生了什么差异。

这是三个 skill 的共同底层哲学。不是"这个词的定义是什么"，而是"这个词在当前任务中改变了什么"。

## 2. dbs-goal：目标清晰化

### 2.1 核心机制

**意义即使用**：

> 目标语言至少要完成两项工作：
> 1. 让下一步行动能够确定
> 2. 让完成状态能够识别

### 2.2 语义做工检测

**检查词语是否改变以下任一项目**：
- 交付物
- 使用对象
- 范围或格式
- 执行路径
- 验收结果
- 资源或风险边界

**只要改变其中一项，这个词就在做工作**。

**例子**：
- "交付一份 **CSV 格式**的数据表" → "CSV 格式"改变了交付规格，在做工作
- "做个**更好的** PPT" → "更好"没有改变可观察的验收标准，不在做工作

### 2.3 家族相似性（5 条特征）

用 5 条特征识别目标成熟度，**不把它们设成统一硬门槛**：

1. **可指物性**：完成时存在可指认的文件、数字、行为、事件或状态
2. **可否证性**：存在能够判断未完成的边界
3. **有完成态**：任务能够在某个条件下结束
4. **语法健全**：谁做、做什么、做到什么程度能够被理解
5. **嵌在上下文里**：与用户当前的资源、约束和处境兼容

**设计洞察**：

> 通常满足其中三项即可形成可用目标。只要"下一步行动"和"完成状态"已经明确，就优先放行。

### 2.4 阻塞性缺口识别

**阻塞性缺口必须满足以下条件之一**：
- 不同答案会产生不同交付物
- 不同答案会改变主要执行路径
- 不同答案会改变是否验收通过
- 擅自假设会带来明显返工、风险或价值偏离

**非阻塞性缺口的处理**：
- 能从上下文安全推出 → 直接提取
- 低风险且容易纠正 → 给出候选判断："我先按「只使用公开数据」执行。如果你希望加入内部数据，再告诉我即可。"

### 2.5 提问纪律

**每次提问前先在内部完成判断**：
1. 这个答案是否已经存在于上下文？
2. 能否从用户给出的规格安全推出？
3. 不同答案是否会改变交付物、路径或验收？
4. 此刻提问能否带来新的决策信息？

**前两项任一为"是"，直接提取。后两项任一为"否"，取消提问。**

### 2.6 路径选择

| 路径 | 条件 | 处理 |
|------|------|------|
| **A：已经可以执行** | 交付物清楚、下一步能确定、完成条件能判断 | 直接放行，输出简洁目标卡 |
| **B：存在阻塞性缺口** | 缺口会改变交付物 / 执行路径 / 验收结果 | 只问 1 个最有信息量的问题 |
| **C：表达仍是愿望** | 用户只说"做个人 IP""变得更好" | 使用条件测试（可指物、完成边界、失败边界） |
| **D：当前目标可能只是手段** | 价值完全依赖后续结果 | 手段—目的测试："你希望做到这一步以后，具体带来什么变化？" |

### 2.7 设计洞察

**dbs-goal 的本质**：

> 不是"帮用户定目标"，而是"判断用户说的话能否指导行动、能否识别完成"。

关键是：
- **不重复询问用户已经提供的信息**
- **不把所有测试设成固定问卷**
- **不强迫明确任务接受完整目标审计**
- **一次只问 1 个问题，等待回答后重新判断**

## 3. dbs-jtbd：任务澄清

### 3.1 核心机制

**先看进展，后看方案**：

> 用户说"帮我写一篇文章""我需要一个课程""给我做一个 Agent"时，先不要把这句话直接当成需求结论。它通常只说明了用户想到的方案。

**先找这条链**：
```
情境 → 卡住的进展 → 想得到的结果 → 当前方案 → 选择标准
```

### 3.2 任务陈述格式

> 当我处于 `{情境}`，我想要 `{推进的进展}`，以便 `{得到的结果}`。

**关键要求**：
- "进展"要写成**变化**，如"把混乱的访谈整理成能做决策的判断"
- 不要只复述**动作**，如"整理访谈"
- "结果"要落在**用户能感知的状态、风险或机会**，避免空泛的"提升效率"

### 3.3 三层任务

| 层次 | 要找什么 | 例子 |
|------|---------|------|
| **功能任务** | 要完成的实际进展 | 在开会前形成可执行的方案 |
| **情绪任务** | 希望摆脱或获得的感受 | 不再担心自己漏掉关键风险 |
| **社会任务** | 希望别人如何看待自己 | 让团队觉得方案经过充分考虑 |

**设计洞察**：

> 功能任务通常决定交付物；情绪和社会任务常决定表达、阻力与最终选择。

### 3.4 四种切换力量

| 力量 | 要判断的问题 |
|------|-------------|
| **推力** | 旧做法造成了什么具体损失、压力或阻塞？ |
| **拉力** | 新方案承诺了什么更好的进展？ |
| **焦虑** | 用户担心新方案会带来什么代价或失败？ |
| **习惯** | 旧做法为什么仍能被继续容忍？ |

**设计洞察**：

> 一个方案被采用，通常需要推力和拉力强过焦虑与习惯。输出建议时要处理这四种力量，不能只放大卖点。

### 3.5 翻译方案语言到任务语言

**拆出三个部分**：
- **表面请求**：他让 AI、产品或服务交付什么
- **任务假设**：他想推进的进展
- **预期结果**：完成后能少承受什么风险、得到什么机会或进入什么状态

**处理方式**：
- 若表面请求与任务一致 → 直接推进
- 若两者存在错位 → 说明错位及其后果，再给出更贴近任务的交付方式
- 保留用户原先方案作为候选，不要武断否定

### 3.6 可观察的选择标准

**从材料中提炼 3–5 个可判断的标准**：
- **必须满足**：不满足就不会被雇用
- **加分项**：能提高选择概率
- **可接受代价**：用户愿意为进展付出的时间、钱、学习或风险

**标准要可观察**：

把"简单好用"还原为"第一次使用 10 分钟内能否得到可修改的结果"这类表述。

### 3.7 设计洞察

**dbs-jtbd 的本质**：

> 不是"做需求调研"，而是"翻译方案语言到任务语言"。

关键是：
- **从材料中提炼任务陈述，不机械追问**
- **只问会改变建议的最小问题**
- **问题优先问具体事实**（如"你上一次试图解决这件事时，卡在了哪一步？"）
- **不问宽问题**（如"你的痛点是什么""你的目标用户是谁"）

## 4. dbs-skill-maker：Skill 制作器

### 4.1 核心机制

**从问题到候选 Skill 的转换**：

```
问题契约 → 行为契约 → 候选生成 → 分级验证
```

### 4.2 问题契约

**至少明确**：
```markdown
反复出现的问题：
使用情境：
用户想推进的变化：
Skill 应交付的结果：
完成证据：
不处理的近邻问题：
```

**设计洞察**：

> 问题太一次性、成功无法观察、主要结果依赖不可获得的权限或事实时，说明当前不适合沉淀。

### 4.3 行为契约

**把"好用、聪明、专业"等要求改写成可观察行为**：

```markdown
目标任务：
预期使用条件：
输入变化范围：
必须做到：
禁止出现：
允许变化：
关键失败：
```

**例子**：
- ❌ "要足够聪明" → 无法验证
- ✅ "能从上下文提取已有信息，不重复询问" → 可验证

### 4.4 分级验证

| 等级 | 证据 | 允许的表述 |
|------|------|-----------|
| **1. 结构校验** | frontmatter、引用、资源和脚本静态检查通过 | "结构校验通过" |
| **2. 行为冒烟** | 候选 Skill 完成至少 1 个真实主要任务 | "行为冒烟测试通过" |
| **3. 留出／回归** | 执行者未看预期答案，留出样本通过且无关键回归 | "当前留出与回归样本通过" |
| **4. 安装交付** | GitHub 来源可用 `npx skills add` 安装，并逐项核对资源 | "GitHub `npx` 安装与资源校验通过" |

**设计洞察**：

> 未实际运行行为任务时，只能报告第 1 级。没有留出收益或出现关键回归时，不能宣称 Skill 已经变强。

### 4.5 判断当前状态

| 当前证据 | 当前任务 |
|---------|---------|
| 只有一个想法，问题和完成态不清 | 形成问题契约与完成条件 |
| 问题已清楚，关键判断缺少机制支撑 | 研究并筛选可用机制 |
| 问题、行为和边界已经清楚 | 生成或补全 Skill 文件 |
| 已有候选 Skill，尚无行为证据 | 建立样本并测试候选 |
| 已有失败输出或用户反馈 | 归因、提出最小修改并回归 |
| Skill 已通过当前验证 | 完成本地交付并提醒可选发布 |

**设计洞察**：

> 不要强迫用户重新走已经完成的阶段。每次先读取当前对话、用户提供的文件和目标目录，只处理当前最需要推进的状态。

### 4.6 不变量（9 条）

1. **从问题开始**：先确定 Skill 反复解决什么问题、在什么情境使用、出现什么证据算完成
2. **保留用户选择**：用户已经给出的名称、目标、平台和边界直接沿用
3. **理论按需进入**：只有理论能够改变判断步骤、适用边界或验证方式时才研究
4. **直接生成文件**：用户要求制作时，交付真实 Skill 目录；材料足够时不把方案说明冒充成品
5. **主入口保持轻**：`SKILL.md` 保存共同决策、关键流程和停止条件；条件性细节放进 `references/`
6. **用行为验证**：测试可观察输出、工具动作和边界，不要求模型展示隐藏推理
7. **失败驱动修改**：修改必须能够解释一类稳定失败，并检查留出样本和关键回归
8. **外部动作单独授权**：创建远端仓库、push、tag、Release 和公开测试材料，都需要用户明确要求
9. **用户参与需求分析**：默认用户具备基础专业能力

## 5. 三个 skill 的对比

| 维度 | dbs-goal | dbs-jtbd | dbs-skill-maker |
|------|---------|----------|----------------|
| **输入** | 模糊目标 / 愿望 | 方案语言（"写文章""做课程"） | 反复问题 / 想法 |
| **输出** | 可执行的目标卡 | 任务陈述 + 选择标准 | 可验证的 Skill |
| **核心判断** | 能否指导行动、能否识别完成 | 方案是否服务任务 | 问题是否适合沉淀 |
| **阻塞性缺口** | 会改变交付物 / 路径 / 验收 | 会改变建议 | 会改变设计决定 |
| **验证方式** | 目标卡的 5 条特征 | 选择标准的可观察性 | 4 级行为验证 |

## 6. 可提取的元 skill 设计模式

### 6.1 模式 1：「意义即使用」判断

```
词语 → 检查是否改变（交付物 / 路径 / 验收）→ 
  改变 → 保留并明确
  不改变 → 标记为"暂未做工"
```

**可复用点**：
- 不问"这个词的定义是什么"
- 问"这个词在当前任务中改变了什么"
- 语义做工检测是判断阻塞性缺口的基础

### 6.2 模式 2：「阻塞性缺口」识别

```
候选问题 → 判断：
  不同答案是否会改变（交付物 / 路径 / 验收）？
    是 → 这是阻塞性缺口，必须问
    否 → 非阻塞性缺口，给候选判断或直接假设
```

**可复用点**：
- 不是所有缺口都需要填
- 只问会改变结果的问题
- 低风险假设优于提问

### 6.3 模式 3：「提问前四重判断」

```
提问前：
  1. 答案是否已存在于上下文？
  2. 能否从规格安全推出？
  3. 不同答案是否会改变结果？
  4. 此刻提问能否带来新决策信息？

前两项任一为"是" → 直接提取
后两项任一为"否" → 取消提问
```

**可复用点**：
- 避免重复询问
- 避免无效提问
- 提高信息增量

### 6.4 模式 4：「家族相似性」而非硬门槛

```
5 条特征：
  - 可指物性
  - 可否证性
  - 有完成态
  - 语法健全
  - 嵌在上下文里

判断：满足其中 3 项即可放行
```

**可复用点**：
- 不设统一硬门槛
- 允许局部模糊
- 只要"下一步行动"和"完成状态"明确，优先放行

### 6.5 模式 5：「方案语言 → 任务语言」翻译

```
用户输入（方案） → 提取：
  - 情境
  - 推进的进展
  - 预期结果
  - 当前方案
  - 选择标准

判断：方案是否服务任务？
  一致 → 直接推进
  错位 → 说明错位 + 给出更贴近任务的交付方式
```

**可复用点**：
- 不直接接受用户说的方案
- 先理解真实意图
- 再判断方案是否合适

### 6.6 模式 6：「问题契约 → 行为契约」转换

```
问题契约：
  - 反复出现的问题
  - 使用情境
  - 用户想推进的变化
  - 应交付的结果
  - 完成证据
  - 不处理的近邻问题

行为契约：
  - 目标任务
  - 预期使用条件
  - 输入变化范围
  - 必须做到（可观察）
  - 禁止出现（可观察）
  - 允许变化
  - 关键失败（可观察）
```

**可复用点**：
- 从"要解决什么"到"要做到什么"
- 把抽象要求改写成可观察行为
- 行为契约是验证的基础

### 6.7 模式 7：「分级验证」而非一次性验证

```
验证等级：
  1. 结构校验（静态检查）
  2. 行为冒烟（至少 1 个真实任务）
  3. 留出 / 回归（未看预期答案，无关键回归）
  4. 安装交付（实际可用）

报告：实际完成的最高等级
```

**可复用点**：
- 不一次性要求完美
- 明确当前验证覆盖范围
- 诚实报告未验证的风险

## 7. 关键发现总结

### 7.1 dbs 系列的本质是什么？

**不是"帮用户做事"，而是"帮用户想清楚要做什么事"**。

三个 skill 都在做同一件事：
- **从模糊到明确**
- **从方案到任务**
- **从愿望到行动**

### 7.2 为什么需要三个 skill？

**因为"想清楚"本身有三个层次**：
- **dbs-goal**：目标层（"要做什么"）
- **dbs-jtbd**：任务层（"为什么要做"）
- **dbs-skill-maker**：沉淀层（"如何复用"）

每层都有独立的判断标准，强行合并会导致混乱。

### 7.3 什么是"可复用的诊断机制"？

**7 个模式**：
1. 「意义即使用」判断
2. 「阻塞性缺口」识别
3. 「提问前四重判断」
4. 「家族相似性」而非硬门槛
5. 「方案语言 → 任务语言」翻译
6. 「问题契约 → 行为契约」转换
7. 「分级验证」而非一次性验证

## 8. 对建站元技能 2.0 的启示

### 8.1 可直接复用的设计

1. **阻塞性缺口识别**：只问会改变交付物 / 路径 / 验收的问题
2. **提问前四重判断**：避免重复询问和无效提问
3. **家族相似性判断**：不设硬门槛，满足 3 项即可放行
4. **方案语言 → 任务语言翻译**：先理解真实意图，再判断方案
5. **问题契约 → 行为契约转换**：把抽象要求改写成可观察行为
6. **分级验证**：明确当前验证覆盖范围

### 8.2 诊断层的设计方向

**建站元技能 2.0 的诊断层需要回答 3 个问题**：

1. **用户要什么？**（目标判断 ← dbs-goal）
   - 用户说的话能否指导行动、能否识别完成？
   - 是网站、skill、PRD、brief，还是只是想法？

2. **为什么要这个？**（任务判断 ← dbs-jtbd）
   - 用户的真实任务是什么？
   - 方案与任务是否一致？

3. **材料够不够？**（缺口判断 ← dbs 共通机制）
   - 有哪些阻塞性缺口？
   - 只问 1-2 个最有信息量的问题

### 8.3 路由层的设计方向

**根据诊断结果选择执行路径**：

| 诊断结果 | 执行路径 |
|---------|---------|
| 明确要做网站 + 材料丰富 | first-flight（可能是 batch 模式） |
| 明确要做网站 + 材料稀疏 | dbs-jtbd → first-flight |
| 明确要做 skill + 问题清楚 | dbs-skill-maker |
| 明确要做 skill + 问题模糊 | dbs-goal → dbs-skill-maker |
| 只是想法，不确定要什么 | dbs-jtbd → 再次诊断 |

### 8.4 需要创新的地方

**dbs 系列没有但建站元技能 2.0 需要的**：

1. **任务类型判断**：dbs 只判断"能不能执行"，不判断"要执行什么类型"
2. **执行路径编排**：dbs 只做诊断，不做 skill 链式调用
3. **条件分支**：根据诊断结果动态选择后续 skill
4. **Batch 模式**：dbs 都是交互模式，没有一次性骨架生成
