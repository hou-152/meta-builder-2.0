# First Flight 逆向分析

**调研时间**：2026-09-30  
**调研对象**：`~/.agents/skills/first-flight/SKILL.md` + 8 个子 skill  
**调研目标**：深度理解 First Flight 的设计理念，提取可复用的元 skill 设计模式

---

## 1. 核心设计理念

### 1.1 问题假设

**First Flight 的核心假设**：
> 对 AI 来说，'写代码'的瓶颈早已不是代码本身，而是'用户到底想要什么'。

因此，First Flight 把"想清楚"这一步拆成：
- **Step 0**：问题定义（双向钢人论证）
- **6 份 spec 文档**：BRIEF → PRD → DESIGN → ARCHITECTURE → CONTENT → AGENTS
- **1 个实施管理流程**：phases（分阶段验收）

### 1.2 Spec-Driven 哲学

**不写代码，只产出 spec**。代码留给用户复制 spec 到项目后让 AI 写。

这意味着：
- First Flight 是"建站前置工具"，不是"代码生成器"
- 交付物是「可执行的规格说明书」，而非「可运行的代码」
- AI 的角色是「帮用户想清楚」，而非「直接干活」

---

## 2. 为什么是 8 步流程？

### 2.1 步骤依赖关系

```
GRIL (问题定义)
  ↓
BRIEF (项目本质)
  ↓
PRD (功能 + 信息架构)
  ↓
DESIGN (视觉风格)
  ↓
ARCHITECTURE (技术选型)
  ↓
CONTENT (内容填充)
  ↓
AGENTS (AI 入口文档)
  ↓
phases (分阶段实施)
```

**依赖逻辑**：
- **PRD → DESIGN**：产品需求定下来后，自然进入"它长什么样"
- **DESIGN → ARCHITECTURE**：设计风格 / UI 模式（bento grid、复杂动效）会影响 UI 框架选型
- **ARCHITECTURE → CONTENT**：架构定了内容怎么存（flat MD / CMS / JSON），再填内容才知道往哪里放
- **CONTENT → AGENTS**：内容是最后补充的（最容易后期改），最后用 AGENTS.md 把所有文档串起来给 AI 用

### 2.2 为什么 CONTENT 只在首次生成？

**迭代时不再生成 CONTENT.md**，理由：
> 首版上线后，新内容应该通过 CMS / JSON / API 等方式管理，不再用 CONTENT.md 文档。

这反映了一个设计判断：
- **首次开发（0→1）**：内容是 spec 的一部分，需要明确"首页放什么、关于页放什么"
- **后续迭代（1→N）**：内容已经进入 CMS / 数据库，不再是 spec 层面的事

## 3. 「长期文档」vs「迭代产物」的分层设计

### 3.1 文件布局

```
project/
├── BRIEF.md              ← 长期文档（根目录）
├── DESIGN.md             ← 长期文档
├── ARCHITECTURE.md       ← 长期文档
├── AGENTS.md             ← 长期文档
├── CLAUDE.md             ← 长期文档
└── iterations/
    ├── v1-launch/        ← 迭代产物
    │   ├── PRD.md
    │   ├── CONTENT.md    ← 仅首次
    │   └── .plan/
    ├── v2-blog/          ← 迭代产物
    │   ├── PRD.md
    │   └── .plan/
    └── v3-{slug}/
```

### 3.2 分层理由

**长期文档**（根目录）：
- 项目级，所有迭代共用
- 只有"项目级"变更才改（罕见）
- 例子：BRIEF 本质边界扩缩、DESIGN 色彩调整、ARCHITECTURE 换技术栈

**迭代产物**（iterations/v{N}-{slug}/）：
- 迭代级，每次新功能独立目录
- 不污染长期文档
- 可以回溯历史（v1 是什么、v2 改了什么）

**设计洞察**：
> 不要把"v2 要做的页面 / 内容"这种**迭代级**变化塞回 BRIEF 或 DESIGN——它们归当次迭代的 PRD。

这避免了"spec 文件越改越乱"的问题。

## 4. 入口逻辑：如何判断「首次 vs 迭代」？

### 4.1 自动检测机制

**任何时候被激活，第一件事是检查 `./iterations/` 目录**：
- **不存在 / 空** → 首次开发，走完整 8 步
- **存在且有 v{N}-{slug}/ 目录** → 迭代，走简化 2 步（PRD + phases）

### 4.2 用户意图优先

**用户说什么压过自动检测**：
- 用户明确说"这是首次"（即使 iterations/ 存在）→ 尊重用户
- 用户明确说"这是迭代"（即使 iterations/ 不存在）→ 尊重用户
- 但要提示对方注意可能的覆盖风险

**设计洞察**：
自动检测是「辅助判断」，不是「强制规则」。用户的明确意图始终优先。

## 5. 交互模式 vs Batch 模式

### 5.1 两种模式对比

| 维度 | 交互模式 | Batch 模式 |
|------|---------|-----------|
| **触发** | 默认 / 用户说"引导我" | 用户说"非交互" / "我自己填" / "batch" |
| **流程** | 一步一步对话，引导回答 | 一次性生成带 `{{TODO}}` 的骨架 |
| **适合** | 不确定细节，想被引导思考 | 已知要什么，想快速起步 |
| **文件产出** | 完整填好的文档 | 骨架 + TODO 标注，用户自己填 |

### 5.2 Batch 模式的 TODO 标注策略

```markdown
## 一句话定义
{{TODO: 一句话讲清楚"网站类型 + 给谁 + 解决什么"。30-50 字。
  我从你的描述里推测可能是 "XXX"，但请确认。}}
```

**标注原则**：
- **用户明确信息** → 直接填
- **标准默认值**（Astro、Tailwind v4）→ 直接填默认
- **真正需要用户思考的**（长期成功、KPI、域名）→ `{{TODO: ...}}`
- **AI 能给候选的** → 给 2-3 个候选：`{{TODO: 主色候选 #2563EB / #1D4ED8，挑一个或给 hex}}`

### 5.3 Batch 模式额外产出：WHERE-TO-START.md

引导用户按顺序填写：
1. BRIEF.md ← 最重要
2. PRD.md
3. DESIGN.md
4. ARCHITECTURE.md
5. CONTENT.md
6. AGENTS.md

## 6. Sub-Skill 如何传递上下文？

### 6.1 链式调用模式

父 skill 通过**切换到子 skill**来推进流程：
- 完成 GRIL → 切换到 `first-flight-brief`
- 完成 BRIEF → 切换到 `first-flight-prd`
- 完成 PRD → 切换到 `first-flight-design`
- ...

### 6.2 上下文传递方式

**方式 1：读已生成的文件**
- `first-flight-prd` 会读 `BRIEF.md` 作为锚点
- `first-flight-design` 会读 `BRIEF.md` + `PRD.md`
- `first-flight-content` 会读 `PRD.md` 的信息架构

**方式 2：对话历史**
- 子 skill 可以从对话历史中获取上下文
- 但不依赖对话历史（因为用户可能中途退出 / 换会话）

**设计洞察**：
> 文件是唯一真实来源（Single Source of Truth）。对话历史是辅助，不是依赖。

## 7. 设计原则（7 条）

### 7.1 原则清单

1. **Spec 阶段是 0 到 1 only** — 假设项目还没启动
2. **Phase 阶段反复使用** — 首次 + 迭代 + 重构都用同一套
3. **spec-driven** — 不写代码，只产出 spec
4. **路径 A / B 分流** — 识别小白 vs 有经验，用对应措辞
5. **预览再写文件** — 先在对话里展示，用户确认后再写
6. **每步可停** — 写完文件问"接着做下一步吗"，用户说停就停
7. **不越界** — BRIEF 不写功能，PRD 不写视觉，DESIGN 不写代码

### 7.2 关键洞察

**原则 5（预览再写文件）**：
避免"AI 自动写文件 → 用户打开一看不对 → 得重新跑一遍"的浪费。

**原则 6（每步可停）**：
尊重用户节奏。不是所有人都想一口气走完 8 步。

**原则 7（不越界）**：
每个文档只管自己的范围，避免职责混乱。

## 8. 可提取的元 skill 设计模式

### 8.1 模式 1：「检测 + 分支」入口

```
激活时 →
  检测当前情境（文件 / 目录存在性）→
  判断任务类型（首次 / 迭代）→
  告知用户当前路径 + 询问模式（交互 / batch）→
  进入对应流程
```

**可复用点**：
- 自动检测 + 用户意图优先
- 清晰告知"你现在在哪条路径"
- 询问模式后不再重复询问

### 8.2 模式 2：「父 skill 只做导览，子 skill 做实事」

**父 skill**：
- 不做具体内容生成
- 只做路由、解释、切换

**子 skill**：
- 专注一件事（如生成 BRIEF）
- 读锚点文件（如 GRIL 结果）
- 产出明确（一份文档）

**可复用点**：
- 职责分离清晰
- 父 skill 变薄，逻辑在子 skill
- 子 skill 可以独立调用（用户可以单独 `/first-flight-brief`）

### 8.3 模式 3：「长期 vs 迭代」分层存储

```
根目录/
├── 长期文档（项目级，少改）
└── iterations/
    └── v{N}-{slug}/
        └── 迭代产物（版本独立，可回溯）
```

**可复用点**：
- 避免 spec 文件越改越乱
- 清晰的版本边界
- 可以对比 v1 vs v2 的差异

### 8.4 模式 4：「预览 → 确认 → 写文件」

```
生成内容 →
  在对话中展示预览 →
  询问用户"这样可以吗" →
  用户确认 →
  写文件
```

**可复用点**：
- 避免盲目写文件浪费
- 给用户审查机会
- 降低返工成本

### 8.5 模式 5：「每步可停」的链式流程

```
Step 1 完成 → 问"接着做 Step 2 吗？"
  ├─ 是 → 进入 Step 2
  └─ 否 → 停止，告知"你可以随时回来继续"
```

**可复用点**：
- 不强制走完全流程
- 尊重用户节奏
- 降低"一次做太多"的认知负担

### 8.6 模式 6：「Batch 模式的 TODO 标注策略」

```
用户明确信息 → 直接填
标准默认值 → 直接填默认
需要思考的 → {{TODO: ...}}
可以给候选的 → {{TODO: 候选 A / B / C，挑一个}}
```

**可复用点**：
- 平衡"AI 推断"和"用户决策"
- 明确标注"这里需要你"
- 降低 TODO 标注的密度（不是所有空都留空）

## 9. 关键发现总结

### 9.1 First Flight 的本质是什么？

**不是"建站工具"，而是"想清楚工具"**。

它假设用户有模糊想法，通过结构化对话 / 骨架生成，帮用户把想法变成可执行的 spec。

### 9.2 为什么需要 8 步而非 3 步？

**因为"想清楚"本身是多层次的**：
- 本质层（BRIEF）
- 功能层（PRD）
- 表现层（DESIGN）
- 技术层（ARCHITECTURE）
- 内容层（CONTENT）
- 协作层（AGENTS）
- 实施层（phases）

每层都有独立的决策空间，强行合并会导致混乱。

### 9.3 什么是"可复用的元 skill 设计"？

**6 个模式**：
1. 「检测 + 分支」入口
2. 「父 skill 只做导览，子 skill 做实事」
3. 「长期 vs 迭代」分层存储
4. 「预览 → 确认 → 写文件」
5. 「每步可停」的链式流程
6. 「Batch 模式的 TODO 标注策略」

## 10. 对建站元技能 2.0 的启示

### 10.1 可直接复用的设计

1. **入口逻辑**：检测情境（文件 / 目录）→ 判断任务类型 → 告知路径
2. **父子分离**：父 skill 做路由，子 skill 做实事
3. **预览机制**：生成内容先预览，确认后再写文件
4. **每步可停**：不强制走完全流程
5. **Batch 模式**：一次性骨架 + TODO 标注

### 10.2 需要扩展的地方

**First Flight 的局限**：
- 只服务"做网站"这一种任务
- 没有"判断任务类型"的能力（假设用户就是要做网站）
- 没有 skill 链式调用（只有子 skill 切换）
- 没有条件分支（流程是线性的）

**建站元技能 2.0 需要增强**：
1. **诊断层**：判断用户要什么（网站 / skill / PRD / 只是想法）
2. **路由层**：根据诊断结果选择执行路径（可能是 first-flight，也可能是 dbs-skill-maker）
3. **条件分支**：根据中间结果决定下一步（如材料不足 → 先补材料）
4. **跨 skill 编排**：可能需要串联多个 skill（如 dbs-jtbd → first-flight-brief）
